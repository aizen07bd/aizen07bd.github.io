# 3편. 클릭 게임이 아니라 판단 게임으로 만들기 - 핵심 로직 설계

`Hacker Life: Trace`의 핵심은 “화면을 본다”가 아니다. “화면을 보고 판단한다”이다. 플레이어는 조사 항목을 열고, 여러 장의 기록을 확인한 뒤, 어떤 화면을 증거로 남길지 결정한다. 이후 결론을 제출하면 게임은 수집한 증거 조합이 충분한지, 함정 증거가 섞였는지, 결론이 근거보다 앞서 나갔는지를 판정한다.

이 구조는 단순한 퀴즈보다 조금 복잡하다. 정답 하나를 누르는 방식이 아니라, 여러 증거의 조합이 맞아야 하기 때문이다. 또한 모바일 환경에서는 너무 세밀한 조작을 요구하면 피로해진다. 그래서 구현은 가능한 단순하게 유지하면서도, 판단 구조는 보안 분석답게 만들려고 했다.

## 1. 증거는 세션에 저장한다

각 에피소드의 조사 화면에서는 플레이어가 고른 증거를 `sessionStorage`에 저장한다. 서버가 필요 없는 정적 웹 게임이기 때문에, 현재 플레이 세션 안에서 상태를 유지하는 방식이 적합했다.

에피소드 14의 악성코드 분석 화면에는 다음과 같은 구조가 들어간다.

```js
const collectedEvidence = new Map();

function saveEvidence() {
  sessionStorage.setItem('ep14Evidence', JSON.stringify([...collectedEvidence.keys()]));
}

function loadEvidence() {
  JSON.parse(sessionStorage.getItem('ep14Evidence') || '[]').forEach(id => {
    if (evidenceMeta[id]) collectedEvidence.set(id, evidenceMeta[id]);
  });

  if (collectedEvidence.size) {
    firstEvidenceMessageShown = true;
    investigationFooter.classList.add('show');
  }

  renderEvidenceList();
}
```

여기서 중요한 점은 증거 전체 내용을 저장하지 않고 `id`만 저장한다는 것이다. 실제 설명 문구는 `evidenceMeta`에 남겨두고, 저장소에는 플레이어가 어떤 증거를 골랐는지만 기록한다. 이렇게 하면 저장 구조가 단순해지고, 화면을 다시 열었을 때도 같은 증거 상태를 복원할 수 있다.

## 2. 같은 기록을 다시 보면 상태가 유지된다

초기 설계에서 문제가 하나 있었다. 플레이어가 이미 기록한 증거를 다시 열었을 때, 그 화면이 기록된 상태인지 알기 어려웠다. 그래서 조사 화면은 현재 보고 있는 기록이 이미 증거 카드에 들어 있는지 확인하고, 버튼 문구를 바꾼다.

```js
function renderRecord() {
  const current = recordQueue[recordIndex];
  if (!current) return;

  const id = idFromFile(current.file);
  const collected = collectedEvidence.has(id);

  recordTitle.textContent = current.title;
  recordCount.textContent = `${recordIndex + 1}/${recordQueue.length}`;
  recordImage.src = current.file;

  recordStatus.classList.toggle('show', collected);
  recordKeep.classList.toggle('recorded', collected);
  recordKeep.textContent = collected ? '기록됨' : '증거로 기록한다';
  recordSkip.textContent = collected ? '증거에서 제외한다' : '관련 없어 보인다';
}
```

이 로직 덕분에 플레이어는 “이미 봤던 로그인가?”를 알 수 있다. 또한 `관련 없어 보인다`를 누르면 기존 증거에서 제거되도록 만들었다. 잘못 기록한 증거를 되돌릴 수 있어야 분석 게임으로서 자연스럽기 때문이다.

## 3. 증거 기록과 제외는 서로 반대 동작이다

조사 화면의 두 버튼은 단순히 다음 화면으로 넘기는 버튼이 아니다. 하나는 현재 기록을 증거로 남기고, 다른 하나는 증거에서 제외한다.

```js
function collectCurrentRecord() {
  const id = currentRecordId();
  const meta = evidenceMeta[id];

  if (meta) collectedEvidence.set(id, meta);

  saveEvidence();
  investigationFooter.classList.add('show');
  renderEvidenceList();
  window.HLTAudio.play('card');

  if (!firstEvidenceMessageShown) {
    firstEvidenceMessageShown = true;
    showToast('강지호', [
      '증거 카드가 생성되었다. 이번엔 도구 이름보다 화면이 실제 행위를 설명하는지 봐야 한다.'
    ]);
  }
}

recordKeep.addEventListener('click', () => {
  if (!collectedEvidence.has(currentRecordId())) collectCurrentRecord();
  advanceRecord();
});

recordSkip.addEventListener('click', () => {
  const id = currentRecordId();

  if (collectedEvidence.has(id)) {
    collectedEvidence.delete(id);
    saveEvidence();
    renderEvidenceList();
  }

  advanceRecord();
});
```

이 부분은 플레이 감각에 큰 영향을 준다. 사용자는 처음에는 정답처럼 보였던 화면을 증거로 기록할 수 있다. 하지만 나중에 다시 보니 함정이라고 판단되면 증거에서 제외할 수 있다. 분석이란 처음부터 완벽한 선택을 하는 일이 아니라, 새 정보를 보며 판단을 갱신하는 일이기 때문이다.

## 4. 증거 카드는 조사 중에도 꺼내 볼 수 있다

모바일 화면에서는 사용자가 지금까지 무엇을 기록했는지 잊기 쉽다. 그래서 오른쪽에 증거 카드 아이콘을 두고, 언제든 현재 증거 목록을 확인할 수 있게 했다.

```js
function renderEvidenceList() {
  evidenceList.innerHTML = '';

  if (!collectedEvidence.size) {
    const e = document.createElement('div');
    e.className = 'evidence-empty';
    e.textContent = '아직 기록한 분석 화면이 없다.';
    evidenceList.appendChild(e);
    return;
  }

  collectedEvidence.forEach(item => {
    const n = document.createElement('div');
    n.className = 'evidence-item';
    n.innerHTML = `
      <div class="evidence-source">${item.source}</div>
      <div class="evidence-text">${item.text}</div>
    `;
    evidenceList.appendChild(n);
  });
}
```

증거 카드는 “정답 리스트”가 아니다. 플레이어가 직접 고른 자료의 요약이다. 그래서 틀린 증거가 들어 있을 수도 있고, 중요한 증거가 빠져 있을 수도 있다. 결과 화면에서 이 조합이 검증된다.

## 5. 결과 판정은 정답, 함정, 부족한 근거를 함께 본다

초기 에피소드들은 다음 규칙을 따른다.

- 반드시 들어가야 하는 정답 증거가 있다.
- 함정 증거가 하나라도 들어가면 실패한다.
- 정답 일부만 있으면 근거 부족으로 실패한다.
- 결론 선택지가 증거보다 앞서가면 실패한다.

이 방식은 보안 분석의 태도와 잘 맞는다. 예를 들어 피싱 사건에서 문자 링크와 카드 입력 페이지를 봤다고 바로 “휴대폰 전체가 해킹됐다”고 말하면 안 된다. 앱 설치, 권한 허용, 결제 승인 여부까지 확인해야 피해 범위를 제한적으로 말할 수 있다.

후반부 에피소드 14에서는 결론 선택지를 없앴다. 악성코드 분석은 이미 여러 도구를 통해 충분한 증거를 고르는 것이 핵심이기 때문이다. 그래서 결과 화면은 “내가 고른 증거들이 옳은가”를 중심으로 판정한다.

## 6. 미니게임은 사건 성격에 따라 다르게 설계했다

모든 에피소드가 같은 증거 수집 방식이면 금방 지루해진다. 그래서 중간에는 미니게임을 넣었다.

에피소드 8은 화이트보드 포스트잇 퍼즐이다. 지금까지 수집한 사건 흐름을 시간순으로 정리하는 장면이다. 아래 포스트잇을 위쪽 화이트보드로 드래그해 붙이고, 붙인 순서가 브리핑 순서가 된다.

```js
function checkBoard() {
  const problems = [];
  const trap = boardOrder.find(id => cardInfo(id)?.trap);

  if (boardOrder.length < 9) {
    problems.push('화이트보드에 9개 타임라인 카드가 모두 붙지 않았다.');
  }

  if (trap) {
    problems.push('결론이 앞서거나 근거 범위를 넘는 메모가 포함됐다.');
  }

  correctOrder.forEach((id, i) => {
    if (boardOrder[i] !== id) {
      problems.push(`${i + 1}번째로 붙인 포스트잇의 순서가 맞지 않는다.`);
    }
  });

  if (problems.length) {
    renderResult(false, problems.slice(0, 6));
    return;
  }

  renderResult(true, [
    '동아리 PC와 해인 PC의 공통 패턴을 시간순으로 설명했다.',
    '유출과 공격자 귀속을 보류했다.',
    '동아리 PC 원본 보존과 추가 비교 계획까지 포함했다.'
  ]);
}
```

이 장면의 목적은 새로운 증거를 찾는 것이 아니다. 이미 본 자료를 설명 가능한 순서로 정리하는 것이다. 실제 분석에서도 타임라인 정리는 매우 중요하다. 같은 증거라도 순서가 틀리면 해석이 달라질 수 있다.

## 7. 이미지는 확대해서 관찰할 수 있어야 한다

후반부에는 분석 도구 화면이 많아진다. 모바일 화면에서는 글자가 작아질 수밖에 없기 때문에, 증거 이미지를 확대해 보는 기능이 필요했다.

```js
function applyZoom() {
  zoomImage.style.transform =
    `translate(calc(-50% + ${zoomX}px), calc(-50% + ${zoomY}px)) scale(${zoomScale})`;
}

function openZoom() {
  if (!recordImage.src) return;

  zoomImage.src = recordImage.src;
  zoomTitle.textContent = recordTitle.textContent + ' 확대';
  resetZoom();
  zoomViewer.classList.add('show');
}
```

이 기능은 단순 편의 기능이 아니다. 분석 화면을 제대로 읽는 경험을 보장하기 위한 장치다. 특히 악성코드 분석 에피소드에서는 IDA Pro, Ghidra, x64dbg, Sysinternals 같은 도구 화면을 여러 장 확인해야 하므로 확대 기능이 중요하다.

## 8. 사운드는 사용자의 첫 입력 이후 재생된다

브라우저는 자동 재생 정책 때문에 사용자가 아무 동작도 하지 않았는데 BGM을 바로 재생하기 어렵다. 그래서 공통 오디오 컨트롤러는 세션 저장소에 사운드 활성 상태를 저장하고, 사용자의 첫 입력 이후 BGM을 재생하도록 설계했다.

```js
(function () {
  const enabledKey = 'hltAudioEnabled';
  let bgm = null;
  let config = null;
  const sfx = new Map();

  function audioEnabled() {
    return sessionStorage.getItem(enabledKey) === '1';
  }

  function playBgm() {
    loadAudio();
    if (!audioEnabled() || !bgm) return;
    bgm.play().catch(() => {});
  }

  function attachResumeEvents() {
    ['pointerdown', 'touchstart', 'keydown'].forEach(eventName => {
      window.addEventListener(eventName, playBgm, { once: true, passive: true });
    });
  }

  window.HLTAudio = {
    init(options) {
      config = options || {};
      loadAudio();
      attachResumeEvents();
      playBgm();
      document.addEventListener('click', event => {
        if (event.target.closest('button, a')) playSfx('click');
      }, true);
    },
    enable() {
      sessionStorage.setItem(enabledKey, '1');
      playBgm();
    },
    play(name) {
      playSfx(name);
    }
  };
})();
```

각 페이지는 이 공통 컨트롤러를 불러오고, 자신에게 필요한 BGM과 효과음을 설정한다. 클릭음, 카드 기록음, 패널 이동음, 성공/실패 스탬프음이 같은 방식으로 재생된다.

## 9. 실패 피드백은 정답을 직접 알려주지 않는다

게임을 만들면서 중요하게 잡은 원칙이 있다. 실패했을 때 “몇 번이 틀렸고 몇 번이 정답입니다”라고 알려주지 않는 것이다. 그렇게 하면 플레이어는 분석하지 않고 정답표만 외우게 된다.

대신 실패하면 인물이 반론한다. “그렇게 말하려면 새 앱 설치나 권한 허용 기록이 있어야 하지 않겠냐?”처럼 결론의 약점을 짚는다. 구체적인 정답 위치를 알려주지는 않는다. 사용자는 다시 조사 화면으로 돌아가 어떤 증거가 부족했는지 스스로 확인해야 한다.

이 구조는 게임을 조금 어렵게 만들지만, 교육적 가치를 높인다. 보안 분석은 누가 정답을 알려주는 일이 아니라, 스스로 근거를 세우고 반론을 견디는 일이기 때문이다.

## 마무리

`Hacker Life: Trace`의 구현은 복잡한 게임 엔진 없이 정적 HTML, CSS, JavaScript로 구성되어 있다. 하지만 핵심 로직은 단순 클릭보다 한 단계 더 깊게 설계했다.

플레이어는 기록을 보고, 증거를 남기고, 다시 빼고, 결론을 제출하고, 반론을 받는다. 그 과정에서 “보안 분석가처럼 생각하는 법”을 조금씩 익힌다. 이 게임의 핵심 로직은 결국 하나의 질문으로 요약된다.

이 기록은 정말 결론을 뒷받침하는가?
