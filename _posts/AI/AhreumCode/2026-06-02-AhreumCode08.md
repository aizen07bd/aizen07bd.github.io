# 아름코드 개발기 8: 실제 TUI와 로컬 LLM 검증에서 배운 것

아름코드 문서에서 반복되는 태도가 있다.

실제 TUI와 실제 로컬 LLM 검증을 mock이나 문서로 대체하지 않는다는 것이다.

이 프로젝트에서 중요한 검증은 "테스트가 통과했다"만이 아니다. 사용자가 TUI에 실제로 입력하고, LM Studio가 응답하고, parser와 decision gate와 tool runtime과 로그가 함께 움직이는지 보는 것이다.

## E2E는 숫자 맞추기가 아니다

`llm-e2e-todo` 문서의 첫 규칙은 anti-inflation이다.

금지되는 것:

- 숫자를 맞추기 위해 시나리오 추가
- mock-only 검증을 E2E 통과로 표시
- 실패 원인을 보기 전에 새 시나리오 늘리기
- 한 시나리오 실패를 말로만 통과 처리
- 통과하기 쉬운 문장으로 프롬프트 바꾸기

E2E는 구현 번호처럼 10개 단계를 맞추는 문서가 아니다. 실제 제품 흐름과 리스크를 기준으로 사용자가 직접 실행해볼 수 있는 시나리오만 둔다.

## 재검증은 프롬프트 하나를 통과시키는 일이 아니다

문서에는 재검증 규칙도 명확하다.

실패한 프롬프트 하나를 보고 바로 고치면 안 된다. 같은 의미의 프롬프트만 반복해서 통과 여부를 보면 안 된다. 실패 원인을 분류하기 전에 새 구현 작업명을 만들면 안 된다.

재검증은 먼저 프롬프트 세트를 실행하고, 실패를 같은 원인군으로 묶은 뒤, 그 원인군이 실제 제품 계약 위반인지 판단한다.

실패군은 다음처럼 분류한다.

| Failure group | 의미 |
| --- | --- |
| `response-contract` | JSON/framing/payload/schema 위반 |
| `tool-contract` | tool/activity/argument schema 위반 |
| `loop-orchestration` | observation attach, next request, repair chain 문제 |
| `permission-safety` | approval, deny, ManualOnly 경계 문제 |
| `provider-runtime` | timeout, empty response, LM Studio 문제 |
| `tui-rendering` | workspace/prompt/status/persona 렌더링 문제 |
| `logging-evidence` | 로그로 원인 추적이 안 되는 문제 |

이 분류가 있어야 모델 variance와 제품 결함을 섞지 않을 수 있다.

## 실제 실패: answer가 JSON을 깼다

2026-05-15 실제 LM Studio 검증에서 중요한 실패가 있었다.

모델이 code/markdown answer를 JSON `message` 안에 직접 넣었다. quote와 newline escape가 깨지면서 malformed JSON이 됐다. repair 요청을 보냈지만 빈 응답으로 끝났다.

이 실패는 단순한 모델 실수처럼 보일 수 있다. 하지만 제품 관점에서는 계약 결함이었다.

결론은 다음이었다.

- answer 본문도 payload separation 대상이다.
- malformed assistant raw response 전체를 repair request에 그대로 넣지 않는다.
- empty repair response는 별도 failure taxonomy와 observation으로 남긴다.
- 완료 검증은 mock happy path가 아니라 실제 provider transcript 기준으로 한다.

이 실패가 `answer_payload_id + AHREUM_PAYLOAD format="markdown"` 규칙으로 이어졌다.

## 실제 실패: strict contract에도 경계가 흔들렸다

2026-05-18 실제 TUI + LM Studio qwen3 검증에서는 30개 시나리오, 총 90개 입력을 실행했다.

이 검증은 pass가 아니었다.

당시 남은 실패군은 다음과 같았다.

- response framing contract instability
- payload/action ordering instability
- invalid model-generated paths
- excessive tool loop limits
- provider timeout
- 일반 프롬프트 중 `/`가 command input으로 탈취되는 TUI bug

여기서 중요한 것은 수정 방향이다.

parser strictness를 낮추지 않았다. 선행 텍스트 뒤의 `<AHREUM_ACTION>`을 찾아 잘라내는 tolerant parsing을 제거한 상태를 유지했다. 없는 path를 fuzzy match로 고치지도 않았다. 숫자 문자열을 number로 조용히 바꾸지도 않았다.

대신 계약을 정렬했다.

- response boundary contract를 단일 소유자로 둔다.
- payload ordering contract를 schema/repair/tool-loop continuation에 같이 렌더링한다.
- path selection contract를 일반 규칙으로 정리한다.
- tool loop limit 진단 로그에 직전 observation context를 남긴다.
- redacted structured tool argument logging을 추가한다.

이것이 아름코드의 방향이다. 통과시키기 위해 런타임이 몰래 고치는 것이 아니라, 계약과 진단을 강화한다.

## Same tool signature 반복

이후 targeted revalidation에서도 same tool signature 반복이 남았다.

예를 들어 같은 `search_text` candidate가 반복되는 경우가 있었다.

해결 방향은 단순히 loop limit을 올리는 것이 아니었다. 이미 실행한 candidate signature와 observation을 tool-loop continuation request에 넣어, 모델이 같은 후보를 반복하지 않도록 구조화했다.

그리고 runtime invariant도 추가됐다.

- 실행 기록은 signature + observation + observation message를 가진다.
- settled duplicate candidate는 answer continuation으로 redirect한다.
- truncated/next_range duplicate는 next_range_hint를 쓰거나 다른 후보를 내게 한다.
- duplicate redirect도 기존 repeat limit으로 제한한다.

이 접근은 특정 프롬프트 문자열에 맞춘 분기가 아니다. 도구 루프 전체의 구조적 문제를 다룬다.

## Persona 검증은 persona 검증이다

Persona layer 검증도 문서에 남아 있다.

2026-05-19 실제 wide TUI + LM Studio session에서는 고정 팀 persona 흐름과 main runtime 실행이 확인됐다. 하지만 문서는 이것을 persona layer 검증으로 한정한다.

이 태도가 중요하다.

검증 범위를 과장하지 않는다.

Persona가 검증됐다고 해서 full main tool-call quality target이 검증됐다고 말하지 않는다. `cargo test`가 통과했다고 해서 실제 로컬 LLM E2E가 통과했다고 말하지 않는다.

## 최신 벤치 결과가 말하는 것

2026-06-01 인수인계 문서에는 qwen3-4b-instruct-2507 기준 최신 벤치 결과가 남아 있다.

```text
Raw Tool Call Success: 23/30, 76.7%
Repaired Tool Call Success: 30/30, 100.0%
Guarded Task Completion: 30/30, 100.0%
```

이 수치가 중요한 이유는 raw success가 전부가 아니라는 점을 보여주기 때문이다.

모델은 처음부터 완벽하지 않다. 하지만 repair와 guard가 제대로 작동하면 guarded completion까지 갈 수 있다.

아름코드의 제품 가치는 이 차이에 있다.

```text
모델이 처음부터 잘했는가?
깨진 후보를 복구했는가?
복구 후 실제 작업 완료까지 안전하게 갔는가?
```

이 세 가지를 분리해서 봐야 한다.

## 배운 점

실제 TUI + 로컬 LLM 검증에서 얻은 교훈은 명확하다.

첫째, mock은 제품 검증을 대체하지 못한다.

둘째, strict parser를 느슨하게 만드는 것은 쉬운 해결책처럼 보이지만 계약을 흐린다.

셋째, 실패는 원인군으로 묶어야 한다. 단일 프롬프트를 고치면 제품이 좋아진 것처럼 착각하기 쉽다.

넷째, 로그가 없으면 실패를 진단할 수 없다.

다섯째, raw tool call 성공률보다 repair와 guarded completion이 제품 가치를 더 잘 보여준다.

다음 글에서는 남은 과제와 앞으로의 방향을 정리한다.
