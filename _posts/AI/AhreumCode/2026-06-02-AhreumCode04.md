# 아름코드 개발기 4: 로컬 LLM에게 실행권을 주지 않는다

아름코드의 로컬 LLM 응답 계약은 한 문장으로 시작한다.

```text
One local LLM response = exactly one next action candidate.
```

로컬 LLM은 실행자가 아니다. 다음 행동 후보 하나를 제안할 뿐이다.

실행은 아름코드 controller가 한다. controller는 모델 응답을 parse하고, schema를 검증하고, 필요하면 repair를 요청하고, permission을 평가하고, 승인 후 도구를 실행하고, observation을 다시 모델에게 전달한다.

이 구조가 아름코드의 핵심이다.

## 로컬 LLM이 loop를 돌지 않는다

문서에서 반복되는 문장이 있다.

```text
The local LLM does not run the loop.
AhreumCode controller runs the loop by repeatedly calling the local LLM after each observation.
```

흐름은 다음과 같다.

```text
1. user prompt 수신
2. controller가 local LLM 호출
3. local LLM이 answer/tool/clarify/blocked 후보 하나 반환
4. controller가 JSON parse, schema validation, tool validation 수행
5. tool 후보이면 repair/approval 수행
6. controller가 tool 실행
7. observation/evidence를 session에 저장
8. observation을 포함해 local LLM을 다시 호출
9. answer/clarify/blocked 또는 loop guard까지 반복
```

이렇게 해야 로컬 LLM의 불안정성을 제어할 수 있다.

모델에게 "알아서 여러 도구를 순서대로 실행해"라고 하면 JSON과 tool arguments가 더 많이 깨진다. 대신 매 turn마다 다음 행동 하나만 받는다.

## 허용되는 응답 타입

로컬 LLM 응답은 다음 중 하나다.

```text
answer
tool
plan
clarify
blocked
```

금지되는 것은 명확하다.

- 한 응답에 여러 tool call 넣기
- 자연어와 JSON 섞기
- JSON 외 markdown/code fence 출력
- 소스코드, patch, 긴 markdown을 JSON string 안에 직접 넣기
- 모델 응답을 confirmed execution으로 바로 취급하기

응답 envelope는 고정되어 있다.

```json
{
  "response_type": "tool",
  "activity": "Explore",
  "message": "I need to inspect the project context first.",
  "tool_name": "read_file",
  "arguments": {
    "path": "docs/PROJECT-CONTEXT.md",
    "start_line": 1,
    "max_lines": 120
  },
  "reason": "The project context routes current decisions."
}
```

`confidence`와 `expected_next`는 제거됐다.

이유도 중요하다. 로컬 LLM의 confidence는 실행 근거가 아니다. `expected_next`는 모델이 숨은 plan을 남기는 방식으로 동작할 수 있다. 다음 행동 판단은 controller가 해야 한다.

## JSON은 제어 정보만 담는다

로컬 LLM은 코드, markdown, patch, 긴 파일 내용을 JSON string에 직접 넣으면 자주 깨진다.

따라서 아름코드는 raw payload separation 규칙을 둔다.

```text
JSON carries control data.
Raw payload blocks carry source/code text.
```

예를 들어 patch는 JSON arguments에 직접 넣지 않고 `payload_id`만 둔다.

```text
<AHREUM_ACTION>
{
  "response_type": "tool",
  "activity": "Change",
  "message": "I can prepare the requested patch.",
  "tool_name": "apply_patch",
  "arguments": {
    "payload_id": "patch_001"
  },
  "reason": "The change requires a patch payload."
}
</AHREUM_ACTION>

<AHREUM_PAYLOAD id="patch_001" format="apply_patch">
*** Begin Patch
*** Update File: src/main.rs
@@
-println!("old");
+println!("new");
*** End Patch
</AHREUM_PAYLOAD>
```

중요한 점은 이 framing이 실행 권한을 의미하지 않는다는 것이다. 이것은 candidate를 안정적으로 전달하기 위한 포맷일 뿐이다.

## Multi-target patch도 하나의 후보일 수 있다

문서에는 이후 중요한 수정도 들어갔다.

`One response = one action candidate` 규칙은 유지하지만, 하나의 `apply_patch` payload 안에는 여러 file target이 들어갈 수 있다.

예를 들어 html/css/js로 분리된 웹게임 프로젝트를 만들 때, 모델은 세 개의 tool call을 내는 것이 아니라 하나의 atomic change proposal을 낼 수 있다.

```text
One response       = one action candidate
One Change action  = one apply_patch payload
One patch payload  = one or more file targets
```

이 계약은 실제 검증에서 나온 필요다. 하나의 patch payload 안에 `index.html`, `styles.css`, `game.js`가 들어왔는데 기존 runtime은 target count 1개만 허용해 차단했다. 그래서 multi-target apply_patch가 다음 capability로 기록됐다.

중요한 것은 이것이 "여러 tool call 허용"이 아니라는 점이다. 여전히 하나의 후보, 하나의 atomic change proposal이다.

## 24개 방어 코드

아름코드는 tool-call 방어를 프롬프트 감으로 처리하지 않는다.

벤치마킹과 실제 실패에서 나온 방어 축은 24개로 정리됐다. 핵심 묶음은 다음과 같다.

| 영역 | 방어 예 |
| --- | --- |
| 응답 계약 | Tool Manifest Echo Check, Partial Tool Block State, schema-first gate |
| 파일 변경 | Two-Phase Mutation, Precondition Snapshot, Patch Impact Guard |
| 출력과 증거 | Observation Schema, Truncation Contract, Full Output Artifact |
| 반복 실패 | Repeat Failure Circuit Breaker |
| command와 권한 | Command Capability Split, Shell-Free Command Schema |
| 경로와 외부 접근 | No Silent Normalization, External Path Permission Branch |
| 네트워크 | Network/Web Permission Branch |
| 변경 후 진단 | Post-Edit Diagnostics Hook |

이 방어의 목적은 모델을 "잘 믿기"가 아니라 모델 출력을 실행 가능한 후보로 검증하는 것이다.

## 깨진 응답을 보정해서 성공 처리하지 않는다

문서에서 강조하는 원칙은 다음이다.

```text
모델 출력은 후보다.
계약 위반은 진단한다.
깨진 응답을 보정해서 성공 처리하지 않는다.
```

예를 들어 parser가 선행 텍스트 뒤의 `<AHREUM_ACTION>`을 찾아 잘라내서 통과시키는 tolerant parsing은 제거됐다. integer string을 number로 바꾸는 normalization도 제거됐다.

이런 보정은 단기적으로 성공률을 높여 보일 수 있다. 하지만 제품 계약을 흐리게 만든다. 모델이 계약을 어겼는지, 런타임이 조용히 고쳤는지 알 수 없게 된다.

아름코드는 이 방향을 피한다.

## tool argument boundary

도구 인자도 실행 직전에 검증한다.

예를 들어:

- unknown argument field 거부
- 필수 argument 누락 거부
- workspace-relative path 검증
- absolute path, `..`, control character path 거부
- limit/range field 경계 검증
- URL은 `http://` 또는 `https://`만 허용
- command `argv`는 비어 있지 않은 string array만 허용

중요한 것은 runtime이 path, URL, argv, payload id를 조용히 normalize하지 않는다는 점이다. 없는 경로를 fuzzy match로 고쳐서 실행하면 모델 실패가 숨겨진다.

## 답변도 payload separation 대상이다

실제 LM Studio 검증에서 중요한 실패가 있었다.

모델이 code/markdown answer를 JSON `message` 안에 직접 넣었고, escape 실패로 malformed JSON이 됐다. repair 요청이 갔지만 빈 응답으로 끝났다.

이 사례 때문에 answer도 payload separation 대상이 됐다.

코드나 markdown이 긴 답변은 `answer_payload_id + AHREUM_PAYLOAD format="markdown"`을 사용한다.

이 실패는 mock 테스트가 아니라 실제 provider transcript에서 나온 제품 실패였다.

## 이 편의 결론

아름코드에서 로컬 LLM은 명령자가 아니다.

로컬 LLM은 다음 행동 후보를 낸다. controller가 그 후보를 계약으로 검증하고, 필요하면 repair하고, policy/permission을 거쳐 실행한다. 실행 결과는 observation으로 남고, 다음 turn의 근거가 된다.

이 구조가 없으면 로컬 LLM tool calling은 데모에서는 되는 것처럼 보이지만 실제 제품에서는 쉽게 무너진다.

다음 글에서는 후보가 실행 가능해도 언제 진행하고, 언제 묻고, 언제 막아야 하는지 다룬다. Intent Frame, Uncertainty Gate, Guide/Crew/Pilot 모드 이야기다.
