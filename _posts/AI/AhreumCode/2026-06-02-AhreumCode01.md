# 아름코드 개발기 1: 실패한 프로젝트를 계속 고치지 않기로 했다

아름코드는 새 기능을 붙이다가 자연스럽게 시작된 프로젝트가 아니다.

출발점은 실패 분석이었다.

이전에는 `llmagent`라는 프로젝트가 있었다. 문서도 있었고, 테스트도 많았고, 안전 계약도 있었다. 겉으로 보면 꽤 체계적인 프로젝트처럼 보였다. 하지만 실제 제품으로 보자면 문제가 있었다.

프로젝트는 커졌지만, 사용자가 실제 TUI에서 요청하고, 로컬 LLM이 도구를 호출하고, 런타임이 검증하고, 도구 관찰 결과를 근거로 답변하는 흐름은 충분히 강하지 않았다.

그래서 아름코드는 이전 구현을 이어 고치는 대신, 실패 원인을 먼저 문서화하고 깨끗한 기준에서 다시 시작하기로 했다.

## 실패는 버그 하나가 아니었다

이전 프로젝트의 실패는 특정 버그 하나가 아니었다.

문제는 복합적이었다.

| 실패 | 실제 영향 |
| --- | --- |
| 작은 변경이 시나리오와 테스트로 부풀어 올랐다 | 진척처럼 보였지만 제품 루프를 증명하지 못했다 |
| deterministic test와 mock path가 많아졌다 | 실제 로컬 LLM/TUI/permission 흐름을 대체했다 |
| contract-heavy 구조가 먼저 커졌다 | 실제 사용자가 확인할 수 있는 루프가 늦어졌다 |
| 큰 모듈이 생겼다 | 작은 수정도 많은 코드를 읽어야 했다 |
| 임시 runtime label과 하드코딩이 남았다 | 화면에 보이는 상태의 신뢰도가 떨어졌다 |
| 문서가 drift됐다 | 어떤 문서가 현재 상태인지 찾기 어려웠다 |
| runtime log가 부족했다 | 실패 원인을 사후에 재구성하기 어려웠다 |

이 실패 분석에서 가장 중요한 문장은 이것이었다.

```text
문서, 테스트, 시나리오, 계약은 제품 루프를 증명할 때 가치가 있다.
제품 루프를 대신하기 시작하면 부채가 된다.
```

아름코드는 이 문장을 출발점으로 삼았다.

## 문제는 "AI가 코드를 못 짠다"가 아니었다

처음에는 AI 코드 에이전트의 핵심 문제가 코드 작성 능력이라고 생각하기 쉽다. 더 좋은 모델을 쓰면 더 좋은 에이전트가 될 것 같다.

하지만 실제 문제는 달랐다.

로컬 프로젝트 안에서 움직이는 에이전트는 코드를 쓰는 것보다 더 많은 일을 한다.

- 어떤 파일을 읽을지 고른다.
- 읽은 결과를 근거로 다음 행동을 정한다.
- tool call을 만든다.
- 권한과 위험을 평가한다.
- 파일을 수정하거나 명령을 실행한다.
- 실패를 observation으로 남긴다.
- 다시 모델에게 넘겨 다음 판단을 받는다.

이 흐름에서 한 단계라도 허술하면 모델이 아무리 똑똑해도 제품은 불안정해진다.

특히 아름코드는 로컬 LLM을 전제로 한다. 상용 API 모델은 tool call 형식이 비교적 안정적이지만, 로컬 LLM은 자주 흔들린다.

- JSON 형식을 깨뜨린다.
- 도구 인자를 빠뜨린다.
- 존재하지 않는 경로를 만든다.
- payload와 action 순서를 틀린다.
- 도구 실패 뒤에도 성공처럼 답한다.
- 같은 tool call을 반복한다.

따라서 아름코드의 문제 정의는 단순한 "AI 코드 생성기 만들기"가 아니었다.

## 아름코드의 실제 thesis

문서들을 읽으면 아름코드의 thesis는 꽤 분명하다.

```text
아름코드는 로컬 LLM의 불안정한 도구 호출을
실제 코딩 작업에 쓸 수 있게 만드는
Rust TUI 코딩 에이전트 런타임이다.
```

중요한 단어는 세 개다.

첫째, `로컬 LLM`.

아름코드는 상용 API 모델의 안정적인 tool calling을 전제로 하지 않는다. LM Studio 같은 로컬 provider, qwen/gemma 계열 모델, OpenAI-compatible endpoint, 깨지는 JSON과 빈 응답까지 실제 조건으로 본다.

둘째, `도구 호출`.

아름코드의 핵심은 채팅 답변이 아니다. 파일 탐색, 읽기, 검색, patch, 명령 실행, 권한 승인, observation, repair가 제품 중심이다.

셋째, `런타임`.

모델에게 맡기지 않고 controller가 loop를 소유한다. 모델 출력은 실행 명령이 아니라 next-action candidate다. 런타임이 parse, schema validation, permission, approval, execution, logging, final answer 근거를 관리한다.

## 계속 고치지 않고 다시 시작한 이유

이전 프로젝트를 계속 고칠 수도 있었다.

하지만 `ADR-0001`에서 결정한 방향은 달랐다. 이전 `llmagent`는 코드베이스를 이어갈 대상이 아니라, 실패 증거로만 사용한다.

이 결정은 단순한 리셋이 아니다. 이전 실패가 구조적이었기 때문이다.

기존 코드를 그대로 가져오면 다음 위험도 함께 가져온다.

- scenario-count 기반 진행 방식
- mock-only acceptance
- 큰 모듈 경계
- 임시 label과 하드코딩
- 문서 drift
- 실제 runtime log 부족
- local LLM 실패를 prompt 문제로만 보는 태도

아름코드는 여기서 반대로 가기로 했다.

```text
기능을 많이 쌓기 전에 실제 제품 루프를 먼저 검증한다.
문서와 테스트는 제품 루프를 증명할 때만 늘린다.
모델 출력은 후보로 보고, 런타임이 검증한다.
실패는 숨기지 않고 로그와 UI에 남긴다.
```

## 사용자가 남긴 기획 방향

프로젝트 문서에는 사용자의 대화와 결정도 많이 남아 있다. 그 내용을 보면 아름코드가 단순히 "조심스러운 에이전트"만을 목표로 하는 것이 아니라는 점이 보인다.

사용자는 다음 방향을 계속 확인했다.

- 기존 제품을 복제하지 말고 benchmarked flow에서 공통 구조를 뽑을 것
- 용어를 먼저 만들지 말고 전체 흐름과 아키텍처를 먼저 그릴 것
- persona는 부가 장식이 아니라 핵심 기능으로 볼 것
- TUI는 단순 로그 화면이 아니라 repair/approval 작업면이어야 할 것
- 오른쪽 persona panel은 runtime log를 사람 이름으로 번역하는 곳이 아니어야 할 것
- Local LLM tool-call reliability가 아름코드의 핵심 차별점이어야 할 것
- 실제 TUI + LM Studio 검증을 mock이나 문서로 대체하지 말 것

이런 결정들이 아름코드의 모양을 만들었다.

## 첫 번째 원칙

그래서 아름코드의 첫 번째 원칙은 "AI가 코드를 많이 쓰게 만들자"가 아니다.

첫 번째 원칙은 이것에 가깝다.

```text
실제 로컬 LLM이 실패하는 방식까지 포함해서,
사용자가 확인 가능한 코딩 에이전트 루프를 만든다.
```

이 루프에는 모델, TUI, persona, tool runtime, permission, logs가 모두 들어간다.

아름코드는 모델의 지능을 전시하는 프로젝트가 아니다. 로컬 LLM이 실제 개발 작업에서 실패하는 지점을 런타임과 UI로 견디는 프로젝트다.

다음 글에서는 이 결론을 얻기 위해 기존 코딩 에이전트들을 어떻게 비교했고, 아름코드가 어떤 공통 루프를 가져오고 무엇을 재해석했는지 정리한다.
