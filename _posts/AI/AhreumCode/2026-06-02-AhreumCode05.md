# 아름코드 개발기 5: 모드는 권한이 아니라 작업 태도다

아름코드에는 `Guide`, `Crew`, `Pilot`이라는 work mode가 있다.

이 이름만 보면 권한 단계처럼 보일 수 있다. 하지만 문서에서 명확히 구분한다.

```text
Mode = user-facing work autonomy preset
Permission matrix = internal allow/ask/deny capability policy
Intent/uncertainty gate = whether the requested action is clear enough
Hard safety limits = mode보다 우선하는 실행 금지/강제 확인 경계
```

즉 모드는 사용자가 이해하기 쉬운 작업 태도 preset이다. 실제 실행 여부는 activity, concrete tool, target path, command/cwd, network/external access, destructive risk, intent clarity, hard safety limits를 함께 평가한다.

## Guide, Crew, Pilot

이전 프로젝트의 `Human / Angel / God` 개념은 새 프로젝트에서 폐기됐다.

현재 이름은 다음과 같다.

```text
Human -> Guide
Angel -> Crew
God   -> Pilot
```

이전 이름은 제품 표면에 쓰지 않는다.

### Guide

Guide는 ask-first, user-led mode다.

사용자가 주도하고 아름코드는 안내와 보조를 한다. 중요한 행동 전에 확인을 많이 받는다. 기획, 리뷰, 위험 작업, 초보자 흐름에 적합하다.

### Crew

Crew는 추천 기본값이다.

bounded Explore는 자동 허용하고, Change/Execute/Configure는 승인을 받는다. 일상적인 로컬 개발 작업에 맞다.

문서에서 Crew를 기본으로 둔 이유는 분명하다.

- read/search까지 매번 묻는 것은 코딩 에이전트 UX를 답답하게 만든다.
- bounded workspace Explore는 로컬 LLM의 불확실성을 줄이는 데 필요하다.
- Change/Execute/Configure는 여전히 승인받으므로 안전 경계를 유지한다.
- persona/team 컨셉과 가장 잘 맞는다.

### Pilot

Pilot은 더 넓은 agent-led mode다.

하지만 "무제한 권한"이 아니다. 사용자가 명시적으로 켜야 하고, hard safety limits는 계속 적용된다.

Pilot도 destructive command, 외부 시스템 영향, secrets, workspace 밖 접근 같은 경계를 우회하지 못한다.

## Intent Frame

모드보다 먼저 필요한 것은 사용자 의도를 구조화하는 일이다.

문서에서는 이를 Intent Frame이라고 부른다.

Intent Frame은 한 요청을 controller가 다루기 위한 구조화된 작업 의도다.

| 필드 | 의미 |
| --- | --- |
| `user_goal` | 사용자가 얻고 싶은 최종 결과 |
| `activity` | 현재 후보 활동 |
| `scope` | workspace, path, file set, command cwd 등 |
| `constraints` | 사용자가 명시한 제한 |
| `known_targets` | 확인된 파일, 디렉터리, 명령, 설정 키 |
| `unknowns` | 아직 모르는 대상, 범위, 값, 영향 |
| `allowed_next` | 지금 안전하게 가능한 다음 행동 |
| `blocked_next` | 지금 하면 안 되는 다음 행동 |
| `evidence` | 읽은 파일, 검색 결과, 승인, observation |

중요한 것은 unknowns를 숨기지 않는 것이다.

모델이 그럴듯하게 target을 골라도, controller가 확인하지 못했다면 unknown으로 남아야 한다.

## Uncertainty Gate

Uncertainty Gate는 불확실성을 어떻게 처리할지 정한다.

결과는 다섯 가지다.

| Outcome | 의미 |
| --- | --- |
| `Proceed` | 안전하고 범위가 명확해서 진행 |
| `ExploreFirst` | 읽기/검색으로 불확실성을 줄인 뒤 다시 판단 |
| `AskUser` | 사용자 확인이나 선택이 필요 |
| `Blocked` | 정책상 수행 불가 |
| `ManualOnly` | 위험도가 높아 아름코드가 직접 실행하지 않음 |

중요한 순서가 있다.

Uncertainty Gate는 permission approval보다 앞선다. 대상과 범위가 불명확한 변경/실행/설정은 approval 화면까지 보내지 않는다.

즉 사용자가 승인한다고 해서 애매한 변경이 실행되는 것이 아니다.

## Activity별 불확실성 정책

아름코드는 activity에 따라 불확실성을 다르게 다룬다.

### Explore

읽기와 검색은 불확실성을 줄이기 위한 안전한 선행 작업이다.

사용자가 파일명을 몰라도 list/search/read로 좁힐 수 있다.

```text
"권한 처리 부분이 어디 있는지 알려줘"
-> ExploreFirst
-> search/read
-> evidence 기반 답변
```

단 workspace 밖, 대량 파일 읽기, 민감 파일, 네트워크 탐색은 별도 permission/hard safety 평가를 거친다.

### Change

변경은 target과 scope가 명확해야 한다.

```text
"그 파일 수정해줘"
-> 대상 불명확
-> AskUser 또는 ExploreFirst 후 AskUser
```

변경 전에는 diff/preview와 approval이 필요하다. 삭제, rename, 대량 변경은 더 엄격하다.

### Execute

명령 실행은 command, cwd, 목적, 예상 영향이 명확해야 한다.

초기 구현에서는 test/build도 approval 대상이다. 장시간 실행, 고부하, 외부 시스템 영향, 프로젝트 전체 영향 가능성이 있으면 ManualOnly 또는 Blocked가 된다.

명령어 문자열을 로컬 LLM 후보 그대로 실행하지 않는다.

### Configure

provider, model, permission, project config 변경은 명시적 intent가 필요하다.

사용자 정의 provider/model 추가는 expanded form 또는 approval을 거친다. 기본값을 임의로 추측해서 저장하지 않는다.

### Ask

Ask는 실패가 아니다.

진행을 안전하게 만들기 위한 판단 지점이다. 사용자가 모른다고 답하면 read/search로 좁힐 수 있는지 보고, 안 되면 Blocked나 ManualOnly로 간다.

## ManualOnly

ManualOnly는 아름코드가 직접 실행하지 않는 안내 전용 상태다.

예를 들어 다음 작업은 직접 실행하지 않는다.

- 전체 삭제, 대량 삭제
- workspace 밖 파일 시스템 변경
- `rm -rf`, 대량 `find -delete`, 대량 권한 변경
- 시스템 디렉터리, 홈 전체, 키체인, credential 접근
- CPU/메모리/디스크 고부하 작업
- 외부 서비스, 배포, 결제, 계정, 인증, 보안 정책 영향
- 프로젝트 전체 구조를 한 번에 바꾸는 대규모 변환

ManualOnly는 AskUser보다 강하다. 사용자가 강하게 요청하거나 승인해도 직접 실행하지 않는다.

## Config는 safety를 끌 수 없다

설정 정책도 이 철학을 따른다.

기본 `.ahreumcode/config.toml`은 얇게 유지한다.

```toml
[provider]
active = "lm-studio"

[mode]
default = "Crew"

[persona]
default = "off"

[web]
enabled = true
```

`/init`을 실행해야 project instruction이 붙고, `/docs-init`을 실행해야 docs 관리 설정이 붙는다.

중요한 점은 config로 hard safety를 끌 수 없다는 것이다.

```toml
[unsafe]
disable_hard_safety = true
```

같은 설정은 허용하지 않는다.

## 이 편의 결론

아름코드에서 모드는 권한 스위치가 아니다.

Guide, Crew, Pilot은 사용자가 이해하기 쉬운 autonomy preset일 뿐이다. 실제 실행은 Intent Frame, Uncertainty Gate, permission policy, hard safety limits가 함께 결정한다.

로컬 LLM이 제안한 후보는 이 경계를 통과해야 한다.

다음 글에서는 아름코드의 독특한 축인 persona를 다룬다. persona는 왜 장식이 아니고, 왜 동시에 tool 권한을 갖지 않아야 하는지 정리한다.
