# 아름코드 개발기 3: TUI는 채팅창이 아니라 작업대다

아름코드는 Rust TUI 애플리케이션이다.

하지만 중요한 것은 "터미널에 채팅창을 만든다"가 아니다. 아름코드의 TUI는 로컬 LLM의 도구 후보를 보고, 검증하고, 승인하고, 실패를 확인하는 작업대여야 한다.

이 관점이 없으면 TUI는 단순 로그 출력기가 된다. 그러면 사용자는 에이전트가 무엇을 하는지, 어떤 근거로 답하는지, 어떤 작업이 실패했는지 알 수 없다.

## 화면 흐름

문서에서 아름코드 TUI는 세 화면 흐름을 가진다.

```text
Intro screen
-> Workspace screen
-> Exit epilogue screen
```

인트로는 첫 입력 중심이다. 처음부터 tool workbench나 persona panel을 열지 않는다. 브랜드 로고와 prompt input, statusline이 중심이다.

종료 화면은 compact epilogue card다. 세션 저장 여부, workspace/model/tool summary, tip 한 줄을 남긴다.

작업 화면은 전체 터미널을 쓰는 main scene이다. 카드형 대시보드가 아니라, 사용자가 계속 일하는 workspace다.

## Intro: 첫 입력 중심

인트로 화면의 결정은 opencode 계열처럼 첫 입력 중심으로 간다.

Codex 계열처럼 시작 카드 안에 모델/디렉터리 상태를 크게 보여주는 방식은 우선순위가 낮다. 상태 정보는 prompt box와 최하단 statusline으로 보낸다.

로고는 한글 대형 픽셀 로고를 보류했다. 이유는 작은 terminal cell 안에서 `아름코드` 자모를 안정적으로 읽히게 만들기 어렵기 때문이다.

현재 방향은 다음이다.

```text
AhreumCode
아름코드 v1.0.0
```

`AhreumCode`는 camel-case block wordmark로 두고, `Ahreum`과 `Code`가 한눈에 분리되게 한다. cyan under-shadow를 쓰되 오른쪽 cursor/bar는 쓰지 않는다. 한글 버전 라인은 로고 bounding width 안쪽 우하단에 맞춘다.

이런 세부 결정은 장식이 아니라 제품 정체성이다. 문서에서는 한글 폭 계산도 `unicode-width` 같은 display-width 기준으로 하라고 명시한다.

## Main scene: 작업 공간

Main scene의 구조는 다음처럼 잡혔다.

```text
AhreumCode v1.0.0
────────────────────────────────────────────────────────
Workspace body
  user prompt block
  manager/persona-derived work decision
  Explore/Change/Execute/Configure/Ask outputs
  evidence / diff / approval result / final answer

[working process] 해석 > 유형 > 검증 > 실행 > 반영 > 답변
[n/6] 작업 내용 (00s, esc 취소)

Prompt composer
Command surface
Statusline
```

중요한 점은 header가 카드가 아니라는 것이다. header는 브랜드 표식만 담당한다.

```text
AhreumCode v1.0.0
```

mode, model, path, context, token 정보는 header에 넣지 않는다. 그런 정보는 statusline으로 내려간다.

## Workspace와 persona 영역

workspace는 main body의 기본 작업 공간이다.

persona가 꺼져 있으면 workspace가 body 전체 폭을 쓴다. persona가 full로 켜져 있을 때만 오른쪽 panel이 생긴다. 즉 persona off는 "빈 오른쪽 영역을 숨김"이 아니라, 우측 영역 자체가 없는 상태다.

오른쪽 persona messenger는 system log를 보여주는 곳이 아니다.

문서에서 반복해서 강조된 경계는 이렇다.

```text
left workspace = official system work events
right persona = social team conversation only
```

도구 실행, 검증, repair, approval, evidence, final answer의 권위는 left workspace에 있다. persona panel은 팀 토론 레이어다. runtime event를 사람 이름으로 번역해서 보여주면 안 된다.

## 6단계 working process

아름코드는 첫 local LLM 응답 전에는 어떤 tool을 쓸지 알 수 없다.

그래서 도구 이름을 미리 보여주는 대신 고정된 6단계 progress skeleton을 사용한다.

```text
[working process] 해석 > 유형 > 검증 > 실행 > 반영 > 답변
[1/6] 로컬 모델 응답 대기 중... (00s, esc 취소)
```

이 strip은 wizard가 아니다. 뒤로 가기나 단계별 입력이 없다. 현재 run이 어디쯤인지 보여주는 진행 표시다.

`Esc`는 현재 run 취소다. retry나 follow-up은 새 run으로 다시 `[1/6]`부터 시작한다.

이 결정은 사용자가 "지금 멈춘 건가, 일하는 건가"를 판단하게 해준다.

## Prompt와 command surface

Prompt composer는 하단 입력 영역이다.

- multiline 기본
- `Enter`는 전송
- `Shift+Enter`는 줄바꿈
- 회색 계열 background
- 긴 입력 wrapping

Slash command는 prompt 아래, statusline 위에 prompt-adjacent surface로 표시한다.

`/` 입력 시 inline command list가 열리고, 키워드로 필터링하며, 방향키와 Enter로 선택한다. 중앙 modal을 기본으로 쓰지 않는다.

문서에서 command surface type은 다음처럼 나뉜다.

| Surface | 용도 |
| --- | --- |
| `InlineList` | `/help`, `/status`, `/model`, `/persona`, `/exit` 같은 명령 목록 |
| `SteppedPicker` | `/mode`, `/provider`, `/persona`처럼 정해진 선택지 |
| `ApprovalDecision` | tool 실행 승인/거절 |
| `ExpandedForm` | 새 provider/model 같은 긴 사용자 정의 입력 |
| `FullscreenView` | 긴 diff, logs, context inspection |

Slash command는 string if문으로 처리하지 않는다. command registry가 name, alias, description, group, availability, presentation, risk, handler를 가져야 한다.

## Statusline

Statusline은 터미널 최하단 1줄이다.

예시는 다음과 같다.

```text
Crew · lm-studio/google/gemma-4-e4b · ~/code/ai/proj/ahreumcode · ctx 18%/82% · tokens 5.8k · web on · Ready
```

포함하는 것:

- current mode
- provider/model
- current project path
- context used/remaining ratio
- token usage
- web state
- runtime state

포함하지 않는 것:

- 긴 session id
- persona state
- 상세 permission matrix
- command count
- help text

상세 정보는 `/status`에서 본다.

Statusline은 장식이 아니라 세션 관측면이다.

## Approval도 prompt-adjacent다

권한 승인 UI도 중앙 modal이 아니라 prompt-adjacent decision surface로 간다.

중요한 규칙은 승인 화면에 모델 설명이 아니라 실제 validated tool request를 보여준다는 점이다.

```text
model output
-> candidate parser
-> validation
-> repair if needed
-> confirmed tool request
-> permission decision surface
-> approve or deny
-> execution or denial observation
-> model loop continues
```

승인 화면에 올라오는 것은 repaired/validated 된 confirmed tool request여야 한다. 깨진 candidate를 그대로 승인받으면 안 된다.

## TUI 결정의 핵심

아름코드 TUI 결정은 예쁜 화면을 만들기 위한 것이 아니다.

사용자가 다음을 구분하게 하기 위한 것이다.

- 모델이 말한 것
- 모델이 제안한 후보
- 런타임이 검증한 것
- 사용자가 승인한 것
- 실제 실행된 것
- observation으로 증명된 것
- 최종 답변에 반영된 것

이 구분이 없으면 로컬 LLM의 실패는 자연어 답변 속에 묻힌다.

다음 글에서는 이런 TUI 위에서 모델 응답을 어떻게 계약화했는지, 왜 "한 응답 = 한 다음 행동 후보" 규칙을 세웠는지 다룬다.
