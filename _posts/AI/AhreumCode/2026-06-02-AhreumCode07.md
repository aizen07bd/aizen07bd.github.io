# 아름코드 개발기 7: 구현은 TUI부터, 완료 기준은 로그까지

아름코드 구현 순서는 일반적인 "코어 먼저" 방식과 다르다.

문서의 핵심 원칙은 이것이다.

```text
먼저 내부 구조를 크게 설계하지 않는다.
먼저 사용자가 입력하고 확인할 수 있는 TUI 기반을 만든다.
기능을 배제해서 작게 만드는 방식이 아니라,
사용자가 테스트 가능한 순서대로 실행 능력을 연다.
```

이전 프로젝트의 실패 중 하나는 core와 contract가 먼저 커지고, 사용자가 실제로 확인할 수 있는 제품 루프가 뒤로 밀린 것이다.

아름코드는 반대로 TUI에서 확인 가능한 흐름을 기준으로 구현한다.

## 8단계 구현 순서

문서의 구현 순서는 다음과 같다.

| 순서 | 내용 |
| --- | --- |
| 1 | TUI 입력 기반 + persona 껍데기 |
| 2 | 로컬 LLM 실제 통신 |
| 3 | JSON 포맷/루프 메시지/중간 저장 |
| 4 | persona 메시지를 실제 run event와 연결 |
| 5 | 안전한 read/search/list tools 열기 |
| 6 | config와 constraint verification |
| 7 | mutation/deletion/execution tools 열기 |
| 8 | session/context sophistication |

이 순서는 시나리오 번호가 아니다. 사용자가 직접 입력하고 확인할 수 있는 능력을 여는 순서다.

## TUI 10단계

첫 단계인 TUI 기반도 다시 10단계로 나뉜다.

| TUI 단계 | 목표 |
| --- | --- |
| `tui-01` | Intro scene |
| `tui-02` | Epilogue scene |
| `tui-03` | Main scene layout |
| `tui-04` | Command area and basic commands |
| `tui-05` | Approval area |
| `tui-06` | Working process area |
| `tui-07` | Workspace output layout |
| `tui-08` | Persona message detail |
| `tui-09` | Complex commands |
| `tui-10` | Modal / expanded form |

각 번호는 구현과 검증 경계다. `tui-01`을 구현할 때 전체 TUI를 검증하지 않는다. 해당 번호의 mockup/render/check만 본다.

이 규칙은 이전 프로젝트의 scenario inflation을 막기 위한 장치다.

## 구현 구조 규칙

아름코드에는 구현 구조 규칙도 따로 있다.

핵심 문장은 다음이다.

```text
의미 있는 단위로 나눈다.
의미 없는 쪼개기는 하지 않는다.
같은 의미를 중복 구현하지 않는다.
각 구현부는 가능한 한 독립적으로 실행/확인 가능해야 한다.
작은 수정이 전체 코드 수정으로 번지면 구조가 잘못된 것이다.
```

금지되는 것은 명확하다.

- 임시방편 코드
- 땜질 코드
- arbitrary hardcoding
- 휴리스틱 코드
- 테스트 통과용 우회
- 현재 화면만 맞추는 임시 UI 분기
- command/tool/mode/provider 문자열을 여기저기 흩뿌리기

이 규칙은 추상적인 코드 품질 이야기가 아니다. 실제로 source audit에서 schema/runtime 불일치, placeholder diff, duplicated version string, heuristic command safety, app.rs God Object 경향 같은 문제가 발견됐기 때문에 생긴 규칙이다.

## Planned UI Implementation Rule

TUI 구현에서는 특히 더 엄격한 규칙이 있다.

사용자에게 보이는 UI는 기획서가 구현 입력이다.

느낌, 기억, 목업의 분위기, 기존 도구의 예시를 근거로 임의 구현하지 않는다.

예를 들어 이런 것은 금지다.

- 계획에 없는 runtime label 삽입
- statusline 최종 결정이 있는데 다른 예시 섞기
- benchmark 이미지의 incidental text를 제품 상태처럼 복사
- 확정된 wordmark를 임의 glyph 조합으로 재해석
- 비어 보여서 그럴듯한 문구 추가

문서의 핵심 문장은 이렇다.

```text
UI 문자열과 상태 표시는 장식이 아니라 제품 의미다.
기획되지 않은 의미는 구현하지 않는다.
```

이 규칙은 `tui-01` intro 구현이 기획 문서와 mockup에서 drift된 뒤 추가됐다.

## No logs, no diagnosis

아름코드의 완료 기준에는 로그가 들어간다.

문서의 핵심 문장:

```text
No logs, no diagnosis.
No diagnosis, no reliable local-LLM tool calling.
```

기능이 화면에 보이거나 테스트가 통과해도, 해당 단계의 diagnostic log가 없으면 완료가 아니다.

로그는 `.ahreumcode/logs/` 아래에 남는다.

```text
.ahreumcode/logs/
  sessions/
    2026-05-15/
      sessions.jsonl
      events.jsonl
      llm.jsonl
      tools.jsonl
      permissions.jsonl
      ui.jsonl
      persona.jsonl
      errors.jsonl
```

화면과 로그는 다르다.

화면은 사용자가 지금 판단해야 하는 요약이다. 로그는 사후 진단을 위한 evidence다.

## 로그가 남겨야 하는 것

로컬 LLM tool calling 문제를 다루려면 다음이 남아야 한다.

| 파일 | 목적 |
| --- | --- |
| `llm.jsonl` | request/response metadata, parse result, repair attempt |
| `tools.jsonl` | tool candidate, validated arguments, execution, observation |
| `permissions.jsonl` | approval request/result, blocked, ManualOnly |
| `ui.jsonl` | scene transition, prompt submit, cancel, exit |
| `persona.jsonl` | persona speaker/message metadata |
| `errors.jsonl` | timeout, parse failure, recoverable error |

민감정보는 저장 전에 제거한다. API key, token, password, private key, `.env` 값은 저장하지 않는다.

로그는 로컬 전용이다. git에 올리지 않는다.

## Test-only world 금지

이전 프로젝트에서 중요한 실패가 있었다.

테스트와 mock LLM 응답이 실제 제품 behavior를 먼저 만들어버리는 패턴이다.

문서에서는 이를 forbidden "test-only world" pattern으로 기록했다.

금지되는 것:

- 테스트가 제품 행동을 발명한다.
- 테스트 이름이 내부 구현 순서를 강제한다.
- mock LLM happy path를 local LLM tool calling 성공 증거로 삼는다.
- runtime log, schema validation, policy decision, TUI flow가 설명할 수 없는 동작을 테스트가 만든다.

테스트는 필요하다. 하지만 테스트가 실제 제품 세계를 대체하면 안 된다.

## 이 편의 결론

아름코드 구현 규칙은 단순히 "깔끔하게 코딩하자"가 아니다.

이전 프로젝트의 실패를 반복하지 않기 위한 운영 체계다.

- 사용자가 확인 가능한 TUI부터 연다.
- 번호별 구현/검증 경계를 지킨다.
- UI 의미는 기획 문서를 따른다.
- 로그가 없으면 완료가 아니다.
- 테스트와 mock은 실제 제품 루프를 대체하지 않는다.

다음 글에서는 이 규칙이 실제 검증 과정에서 어떻게 드러났는지, LM Studio/qwen3 기반 E2E와 벤치 결과를 중심으로 다룬다.
