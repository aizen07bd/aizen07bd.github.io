# 아름코드 개발기 6: 페르소나는 대본 생성기가 아니다

아름코드 문서를 제대로 읽기 전에는 persona를 "오른쪽에 보이는 보조 대화 UI" 정도로 설명하기 쉽다.

하지만 프로젝트 문서에서 persona는 훨씬 중요한 위치를 가진다. 사용자는 이전 AhreumCode 개념에서 persona가 핵심 기능 중 하나였고, 절대 optional polish로 취급하면 안 된다고 명확히 했다.

다만 persona가 실제 도구를 실행하거나 최종 답변 권한을 갖는다는 뜻은 아니다.

아름코드 persona의 핵심은 "협업처럼 보이는 대본"이 아니라, 메인 런타임과 권한 경계를 분리한 고정 팀 대화다.

## 실패한 방향: 한 번에 팀 대화 JSON 생성

초기 방식은 다음과 같았다.

```text
persona_conversation_contract_prompt(...)
  -> "팀장/팀원 대화를 JSON 배열로 만들어줘"
  -> parse_persona_conversation(...)
  -> PersonaBuffer에 일괄 append
```

이 방식은 협업이 아니었다.

로컬 LLM이 하나의 주제를 여러 이름의 대사로 표현하는 것뿐이었다. 각 persona가 독립 맥락과 임무를 가지고 판단하거나 응답하지 않았다.

문제는 명확했다.

- 팀원이 독립적으로 판단하지 않는다.
- 앞 발언을 실제로 받은 것이 아니라 대본처럼 이어진다.
- 한두 마디 뒤에 끝난다.
- 후속 사용자 발화를 새 대본 생성으로 처리한다.
- 실패 원인이나 런타임 상태를 그럴듯하게 꾸며 말한다.

그래서 이 방식은 폐기 대상이 됐다.

## 새 정의: 고정 팀, 독립 speaker turn

아름코드 persona는 다음 구조로 재정의됐다.

```text
사용자 요청
  -> 팀장 persona 턴
  -> 지윤/민호/서연/하준에게 역할별 메시지 전달
  -> 각 멤버 persona가 독립 LLM 턴으로 응답
  -> 팀장이 멤버 의견을 보고 진행 방향 정리
  -> 메인 런타임은 별도 도구/답변 루프 수행
```

팀은 고정이다.

| 인물 | 역할 |
| --- | --- |
| `팀장` | 조율, 소집, 종합 |
| `지윤(기획/설계)` | 요구사항, 범위, 구조 |
| `민호(구현)` | 구현 경로, 기술 선택, 변경 단위 |
| `서연(검증)` | 확인 기준, 실패 가능성, 테스트 관점 |
| `하준(문서)` | 사용자 전달, 기록, 결정 사항 정리 |

멤버를 무한히 늘리지 않는다. 작업마다 전문가를 생성하는 방식은 초기 범위에서 제외됐다.

## Persona는 권한이 없다

이 경계가 가장 중요하다.

Persona는 실제 실행 권한이 없다.

- tool call 실행 금지
- 파일 값/패키지명/버전/설정값 단정 금지
- 최종 답변 권한 없음
- approval/permission 우회 금지
- runtime log를 사람 이름으로 번역 금지
- 실패 원인을 근거 없이 창작 금지

메인 런타임만 도구 실행, evidence 기록, 최종 답변을 담당한다.

즉 persona는 사용자의 이해를 돕는 토론 계층이지, 도구를 조작하는 agent swarm이 아니다.

## 왼쪽과 오른쪽의 경계

TUI에서도 이 경계가 분명해야 한다.

왼쪽 workspace는 공식 작업 이벤트다.

- tool state
- validation
- repair
- approval
- evidence
- final answer

오른쪽 persona panel은 social team conversation이다.

문서에는 실제 실패 사례가 남아 있다. persona panel에 모델/validation/permission/tool status 메시지가 사람 이름으로 표시되었고, 사용자는 이것을 제품 방향으로 틀렸다고 봤다.

persona panel은 system log가 아니다.

```text
left workspace = source of truth
right persona = team discussion layer
```

이 경계가 깨지면 사용자는 persona 발화를 공식 evidence처럼 오해할 수 있다.

## pass가 중요하다

고정 팀이라고 해서 모든 멤버가 매번 말해야 하는 것은 아니다.

문서에서 강조한 규칙은 다음이다.

```text
고정 팀은 고정 발언 슬롯이 아니다.
역할 관점에서 추가할 의견이 없으면 pass하고 UI에 표시하지 않는다.
```

이 규칙이 없으면 persona는 협업이 아니라 순번 보고처럼 보인다.

예를 들어 문서 수정만 하는 작업에서 모든 팀원이 억지로 한마디씩 말하면 오히려 산만하다. 필요한 멤버만 호출되고, 필요 없는 멤버는 pass해야 한다.

## Team Task 상태

초기 구현은 in-memory team task로 시작한다.

```text
팀장 peer_messages
  -> PersonaTeamTask(Open)
  -> 호출된 멤버 turn이 Claim
  -> 멤버 speak 결과로 Reported
  -> 멤버 pass 결과로 Passed
  -> 팀장 summary/completion에서 Closed
```

이 상태는 persona 협업 흐름을 유지하기 위한 구조 데이터다.

중요한 점은 이것이 visible-text denylist가 아니라는 것이다. 특정 한국어 동사나 특정 파일명으로 persona 발화를 거부하는 방식이 아니다.

Persona가 실패하거나 JSON을 깨면 해당 turn은 pass로 처리한다. 메인 런타임의 도구/evidence/final answer 경계는 그대로 유지한다.

## 실제 검증

문서에는 persona layer의 실제 검증도 남아 있다.

2026-05-19 실제 wide TUI + LM Studio session에서 다음 흐름이 확인됐다.

- `팀장` kickoff first
- addressed teammate turns
- `팀장` closure
- main runtime execution
- `list_files`
- normalized `read_file` on `.ahreumcode/config.toml`
- final answer completion

검증 명령도 기록되어 있다.

```text
cargo fmt --check
cargo test
cargo run -- --scene main --smoke
```

단, 문서는 이 검증을 persona layer 검증으로 한정한다. full main tool-call quality target을 검증한 것은 아니다.

이 구분도 아름코드답다. 검증한 것을 검증했다고 말하고, 검증하지 않은 것은 남긴다.

## Persona가 제품에 주는 의미

아름코드에서 persona는 mascot이 아니다.

사용자가 로컬 LLM의 불안정한 tool loop를 이해할 때, 작업을 역할 관점으로 나눠 보는 보조 레이어다.

하지만 그 레이어는 공식 evidence가 아니어야 한다. 도구 실행 권한도 없어야 한다. 최종 답변 권한도 없어야 한다.

정리하면:

```text
Persona는 협업 레이어다.
Runtime은 실행 레이어다.
Evidence는 workspace에 남는다.
Final answer는 main runtime이 낸다.
```

다음 글에서는 이 제품 사상을 실제 구현 순서와 코드 구조 규칙으로 어떻게 바꿨는지 다룬다.
