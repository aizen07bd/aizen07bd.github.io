# 아름코드 개발기 2: 기존 에이전트를 베끼지 않고 흐름을 다시 그렸다

아름코드 기획에서 초기에 중요한 정정이 있었다.

기존 코딩 에이전트를 보고 바로 화면이나 용어를 만들면 안 된다는 것이다. 먼저 성숙한 도구들이 어떤 공통 흐름으로 움직이는지 비교하고, 그 흐름에서 아름코드가 그대로 가져갈 것과 재해석할 것을 나눠야 했다.

이 과정이 없으면 제품은 쉽게 아류가 된다.

## 잘못된 이해

처음에는 코딩 에이전트 흐름을 이렇게 단순하게 볼 수 있다.

```text
model
-> tool call
-> approval
-> execution
-> final answer
```

하지만 문서에서 정리한 결론은 다르다.

성숙한 코딩 에이전트는 단발 구조가 아니다. 핵심은 반복 루프다.

```text
user input
-> session/context
-> model request
-> model response
-> tool validation
-> policy/approval
-> execution
-> observation
-> session update
-> model continuation
-> repeat
-> final answer or blocked state
```

도구 실행 결과는 다시 모델에게 들어가야 한다. 모델은 그 observation을 보고 다음 행동을 정한다. 파일을 읽었으면 그 내용을 근거로 답하거나, 더 읽어야 할 파일을 고른다. 명령이 실패했으면 실패 메시지를 보고 다음 행동을 바꾼다.

아름코드는 이 공통 loop를 새로 발명하는 프로젝트가 아니다. 오히려 이 loop를 인정한 뒤, 로컬 LLM이 그 loop를 자주 망가뜨리는 문제를 다루는 프로젝트다.

## 기존 제품에서 가져올 공통 구조

문서에서는 Claude Code, Codex CLI, opencode, Gemini CLI, Aider, Cline, Goose, Continue 등을 비교했다.

각 제품은 다르지만 공통 구조가 있다.

| 공통 구조 | 아름코드 적용 |
| --- | --- |
| model-tool-observation 반복 루프 | controller가 loop를 소유한다 |
| session/context 유지 | run, turn, observation을 저장한다 |
| tool registry | tool name, schema, activity, permission을 단일 의미로 관리한다 |
| policy/permission/sandbox gate | 실행 전 위험과 권한을 평가한다 |
| approval surface | 위험한 작업은 사용자 결정을 받는다 |
| file tool과 command tool 분리 | Explore/Change/Execute를 나눠 다룬다 |
| observation 기반 final answer | 모델 주장보다 실행 결과를 우선한다 |
| TUI가 core event를 표시 | 화면은 장식이 아니라 작업 상태 표현이다 |

이 구조들은 특정 제품의 개성이 아니라 코딩 에이전트 제품군의 기본 골격에 가깝다.

## 아름코드가 재해석해야 하는 지점

아름코드의 차별점은 기존 흐름을 그대로 복제하지 않는 데 있다.

가장 큰 차이는 모델 출력의 지위다.

상용 API 모델은 tool request를 비교적 안정적으로 낼 수 있다. 하지만 로컬 LLM은 JSON, tool name, arguments, path, payload framing을 자주 틀린다.

그래서 아름코드에서는 모델 출력을 confirmed tool request로 보지 않는다.

```text
local model output
-> next-action candidate
-> parse
-> schema validation
-> tool validation
-> repair or rejection
-> confirmed tool request
-> permission/approval
-> execution
-> observation
```

이 한 단계 차이가 제품 성격을 바꾼다.

아름코드의 핵심은 "도구를 많이 가진 에이전트"가 아니라, "깨지는 도구 후보를 실행 전 계약으로 다루는 런타임"이다.

## Tool request가 아니라 candidate

문서의 중요한 문장은 이것이다.

```text
Local LLM output is a next-action candidate, not trusted intent truth.
```

로컬 LLM이 사용자의 의도, 대상 파일, 실행 범위, 위험도를 항상 올바르게 판단한다고 가정하지 않는다.

예를 들어 모델이 `read_file`을 제안했다고 해서 바로 읽으면 안 된다. 경로가 workspace-relative인지, 존재하는지, 민감 파일은 아닌지, 사용자의 요청과 맞는지 검증해야 한다.

모델이 `apply_patch`를 제안했다고 해서 바로 적용하면 안 된다. patch payload가 완전한지, target이 중복되지 않는지, 기존 파일 수정에는 read evidence가 있는지, 사용자 승인이 필요한지 확인해야 한다.

이 때문에 아름코드에는 candidate parser, schema validation, repair, permission, approval이 제품의 중심 단계로 들어간다.

## Activity taxonomy

도구 이름을 사용자에게 그대로 보여주면 UI가 내부 구현처럼 보인다.

아름코드는 사용자 표면에서 작은 1-depth activity taxonomy를 사용한다.

```text
Explore
Change
Execute
Configure
Ask
```

이 분류는 CRUD식 `file_read`, `file_write`, `file_delete` 표면을 피하기 위한 것이다.

| Activity | 의미 |
| --- | --- |
| Explore | 읽기, 검색, 목록, 웹 검색처럼 근거를 확보하는 일 |
| Change | 파일 생성, 수정, 삭제, patch 적용 |
| Execute | shell command, build, test, process 실행 |
| Configure | provider, model, mode, docs/init 설정 |
| Ask | 사용자 확인, 선택, clarification, approval |

내부 concrete tool은 더 세분화될 수 있다. 하지만 사용자는 "read_file이 실행됐다"보다 "Explore로 프로젝트 근거를 확인했다"를 더 빠르게 이해한다.

## Persona도 loop 안에 들어간다

문서에서 사용자는 persona를 optional polish로 보지 말라고 했다.

다만 persona가 도구 실행 권한을 갖는다는 뜻은 아니다. 아름코드에서 persona는 오른쪽 messenger에 보이는 팀 토론 계층이고, 메인 런타임과 권한 경계가 분리된다.

초기 기획에서는 persona가 다음 역할을 가져야 했다.

- candidate review
- risk critique
- missing-info critique
- repair suggestion
- evidence review
- final synthesis review

이후 구현에서는 persona를 더 엄격히 재정의했다. persona는 tool/evidence/final answer 권한을 갖지 않는다. 대신 고정 팀원들이 역할 관점에서 의견을 주고, 메인 런타임은 별도로 도구와 답변을 처리한다.

이 차이는 뒤의 persona 편에서 다시 다룬다.

## TUI는 approval 화면이자 repair 작업대

기존 에이전트의 UI는 approval과 execution 상태를 보여준다.

아름코드 TUI는 거기서 한 단계 더 필요하다. 로컬 LLM이 잘못된 tool candidate를 만들기 때문에, approval 이전에 candidate를 고치거나 거부하는 표면이 필요하다.

예를 들어 다음 상태들이 TUI에 드러나야 한다.

- malformed JSON
- missing argument
- 없는 path
- payload/action ordering mismatch
- unsafe command
- ambiguous target
- repeated same tool call

사용자는 모델이 낸 후보, 런타임이 검증한 결과, repair 여부, 승인할 실제 confirmed request를 구분해서 볼 수 있어야 한다.

## 최종 흐름

문서에서 제안한 아름코드 전체 흐름은 다음에 가깝다.

```text
User input in TUI
-> Session/context update
-> Local model request
-> Model response candidate
-> Candidate parser
-> Candidate validation
-> Persona/team discussion where enabled
-> Repair path if invalid
-> Confirmed tool request
-> Policy/permission/sandbox
-> Approval if needed
-> Tool execution
-> Evidence observation
-> Session update
-> Local model continuation
-> Repeat until final answer / blocked / cancelled
```

이 흐름에서 아름코드의 개성은 세 곳이다.

첫째, local LLM failure recovery.

둘째, TUI repair/approval surface.

셋째, persona collaboration layer.
