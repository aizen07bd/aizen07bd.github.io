# 아름코드 개발기 9: 다음 과제는 더 많은 기능이 아니라 더 단단한 루프다

아름코드의 다음 과제는 기능을 무작정 늘리는 것이 아니다.

문서 전체를 읽으면 방향은 일관된다.

```text
로컬 LLM이 실패하는 방식까지 포함해서,
사용자가 확인 가능한 model-tool-observation loop를 더 단단하게 만든다.
```

이 기준에서 앞으로의 과제를 정리할 수 있다.

## 1. Multi-target apply_patch

가장 직접적인 다음 capability는 `tool-11-multi-target-apply-patch`다.

실제 검증에서 분리형 웹게임 생성 요청이 실패했다. 모델은 하나의 `apply_patch` payload 안에 `index.html`, `styles.css`, `game.js` 세 target을 넣었다. 하지만 runtime은 target count가 정확히 1개여야 한다고 차단했다.

문서의 결론은 다음이다.

```text
One response       = one action candidate
One Change action  = one apply_patch payload
One patch payload  = one or more file targets
```

즉 여러 파일 변경은 여러 tool call이 아니라 하나의 atomic change proposal이어야 한다.

다만 이것을 구현할 때 조심해야 한다.

- prompt keyword로 해결하지 않는다.
- 특정 파일명 세트를 하드코딩하지 않는다.
- payload를 조용히 여러 tool call로 쪼개지 않는다.
- target별 operation을 파일 상태와 사용자 요청에 맞게 검증한다.
- 승인 화면에는 전체 요약과 target별 요약을 함께 보여준다.
- 실행은 전체 성공 또는 전체 실패로 다룬다.

이 과제는 단순 기능 추가가 아니라 Change activity 계약의 확장이다.

## 2. 실제 검증을 계속 제품 기준으로 유지하기

아름코드는 mock-only 통과를 제품 통과로 보지 않는다.

앞으로도 실제 검증은 다음 기준을 유지해야 한다.

- 실제 TUI 입력
- 실제 로컬 LLM 응답
- 실제 parser/schema/decision/runtime 경로
- 실제 tool observation
- 실제 로그
- 실패 원인군 분류

단일 프롬프트를 통과시키는 식으로 검증하면 안 된다. 실패군을 먼저 모으고, 제품 계약 위반인지 모델 variance인지 provider issue인지 나눠야 한다.

특히 구현 후 재검증은 실패한 프롬프트 하나만 다시 돌리는 방식이 아니다. 같은 원인군에 속한 프롬프트와 다른 원인군 프롬프트를 함께 봐야 한다.

## 3. Tool registry와 단일 의미 소유권 유지

source audit에서 드러난 중요한 문제는 tool name/activity/schema/permission/runtime이 여러 파일의 문자열 match로 흩어질 때 생기는 불일치였다.

앞으로 tool을 늘릴 때는 이 문제가 반복되면 안 된다.

필요한 방향은 다음이다.

- tool registry가 tool name과 activity mapping을 소유한다.
- concrete tool schema가 argument shape를 소유한다.
- permission branch는 registry metadata와 연결된다.
- runtime dispatch는 registry와 불일치하지 않아야 한다.
- schema prompt는 실행 가능한 tool만 안내해야 한다.

모델에게 광고한 tool은 실제 runtime에서 실행 가능하거나, 아직 열지 않은 tool이면 안내하지 않아야 한다.

## 4. TUI repair surface 고도화

아름코드 TUI는 단순 채팅창이 아니다.

앞으로 더 중요해질 표면은 repair와 approval이다.

사용자는 다음을 볼 수 있어야 한다.

- 모델이 낸 candidate
- validation 실패 이유
- repair 요청 여부
- repaired candidate
- confirmed tool request
- risk와 reason
- approval 결과
- execution observation

특히 긴 output은 preview와 artifact로 분리해야 한다. 화면에는 필요한 만큼만 보여주고, 진단용 전체 내용은 로그/artifact로 남긴다.

diff도 placeholder가 아니라 실제 변경 데이터를 보여야 한다. 사용자는 파일이 바뀐다는 사실만이 아니라 어떻게 바뀌는지 확인해야 한다.

## 5. Persona를 팀 대화로 유지하기

Persona는 강력하지만 위험한 UI다.

잘못 만들면 runtime log를 사람 이름으로 번역하는 기능이 된다. 또는 대본 생성기가 된다.

앞으로도 지켜야 할 경계는 명확하다.

```text
Persona has no tool permission.
Persona has no evidence authority.
Persona has no final-answer authority.
```

Persona는 팀 관점에서 작업을 이해하게 돕는 레이어다. 메인 런타임이 도구를 실행하고, workspace가 evidence를 보여주고, final answer는 공식 observation에 기반해야 한다.

고정 팀도 고정 발언 슬롯이 아니다. 필요한 멤버만 speak하고, 역할 관점에서 보탤 말이 없으면 pass해야 한다.

## 6. Logging을 더 실용적인 진단 도구로 만들기

아름코드에서 로그는 완료 조건이다.

하지만 로그가 많기만 하면 충분하지 않다. 실패 원인을 실제로 재구성할 수 있어야 한다.

앞으로 로그에서 더 중요해질 항목은 다음이다.

- redacted tool arguments
- response framing parse result
- payload validation result
- permission decision
- same tool signature repeat
- loop limit diagnosis
- provider timeout/empty response
- UI input boundary event

사용자는 화면에서 요약을 보고, 필요한 경우 로그로 원인을 추적할 수 있어야 한다.

## 7. Config와 init을 얇게 유지하기

기본 config는 얇게 유지한다.

`[instructions]`는 `/init` 이후에 붙고, `[docs]`는 `/docs-init` 이후에 붙는다. 프로젝트 instruction과 문서 관리 기능을 모든 프로젝트에 강제로 묶지 않는다.

이 방향은 아름코드가 모든 repository에 무거운 구조를 강요하지 않기 위한 것이다.

중요한 것은 opt-in이다.

- instruction 관리는 `/init`
- docs 관리는 `/docs-init`
- provider/model 추가는 expanded form
- hard safety는 config로 끌 수 없음

## 8. 공개 문서와 블로그도 제품 루프를 따라야 한다

블로그도 조심해야 한다.

처음 작성한 초안처럼 일반적인 "AI 에이전트는 조심해야 한다" 수준에 머물면 아름코드의 실제 사상이 빠진다.

아름코드의 글은 다음을 드러내야 한다.

- 실패한 `llmagent`에서 왜 다시 시작했는지
- 기존 제품 벤치마킹에서 어떤 공통 loop를 뽑았는지
- 로컬 LLM의 tool-call 실패를 왜 제품 핵심 문제로 보는지
- TUI가 왜 repair/approval 작업대인지
- persona가 왜 대본 생성기가 아닌지
- 로그와 실제 TUI+LM Studio 검증이 왜 완료 조건인지

즉 블로그도 제품 루프를 설명해야 한다.

## 마무리

아름코드는 단순한 AI 코드 생성기가 아니다.

아름코드는 로컬 LLM이 깨뜨리는 model-tool-observation loop를 런타임, TUI, permission, persona, logging으로 견디는 프로젝트다.

이 프로젝트의 방향은 기능 목록보다 실패 처리 방식에서 더 잘 드러난다.

모델 출력은 후보로 본다.

계약 위반은 진단한다.

깨진 응답을 몰래 보정해 성공 처리하지 않는다.

실패는 로그로 남긴다.

TUI는 사용자가 작업을 확인하고 승인하는 표면이다.

Persona는 협업 레이어지만 evidence 권한은 없다.

검증은 실제 TUI와 실제 로컬 LLM 경로로 한다.

아름코드가 앞으로 더 좋아진다면, 그것은 기능이 많아져서가 아니라 이 루프가 더 단단해졌기 때문일 것이다.
